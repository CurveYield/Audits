# ABI Function Fork Simulation Design

## Goal

Create a reproducible real-mainnet-fork simulation harness for the active
CurveYield v18.9 deployment package. The harness must exercise every directly
callable public/external ABI function across all 14 deployed contracts and fail
if any signature is unclassified or untested.

## Scope

The callable inventory is generated from the compiled ABIs for the 14 entries
in `deployment-v18/lib-v18.js::DEPLOYABLES`. The current build contains 743 ABI
function entries, including inherited functions, overloads, constants, and
autogenerated public-variable getters.

Included:

- every public/external ABI signature
- view and pure functions
- state-changing functions
- inherited ERC-20, Votes, ownership, and access-control functions
- successful paths where the required state is reachable
- authorization, invalid-input, boundary, and invalid-state reverts

Excluded:

- internal and private functions, because they are not directly callable
- mock contracts and mock external dependencies
- archived source under `archive-do-not-run/`
- a formal audit PDF; this harness is technical audit evidence

## Runtime Architecture

The entry point will be
`deployment-v18/simulate-all-functions-v18.js`. Focused scenario modules will
live under `deployment-v18/simulation-v18/` so contract-specific setup and
assertions do not become one oversized file.

The entry point will:

1. Start one Anvil mainnet fork using the RPC URL supplied only through an
   environment variable.
2. Pin and report the fork block.
3. Fund ephemeral actors with ETH locally.
4. Deploy and configure all 14 contracts once using the existing deployment
   code.
5. Build the ABI coverage inventory dynamically.
6. Run the opening 15-day yield cycle.
7. Run all contract-specific callable-function scenarios.
8. Use Anvil snapshots and reverts around destructive or mutually exclusive
   scenarios.
9. Restore the canonical post-opening-cycle state.
10. Run the closing 15-day yield cycle.
11. Emit machine-readable JSON and concise Markdown reports.

All contract calls after startup go through the local Anvil endpoint. The
harness will batch reads where practical and will not repeat the deployment or
fork merely to isolate scenarios.

## No-Mock Funding

The harness will use real forked mainnet contracts and balances. It will not
deploy token mocks or replace external contract code.

For external assets such as SDT, the harness will locate a sufficiently funded
real holder from a bounded candidate set, verify the balance, impersonate that
account locally, transfer only the amount needed to ephemeral test actors, and
stop impersonation. Newly deployed CurveYield assets will be obtained through
their intended protocol flows.

If a required live asset cannot be sourced, the harness must fail with an
explicit funding/precondition error rather than silently inserting synthetic
token state.

## Opening and Closing Yield Cycles

Every applicable staking or vault component will participate in both cycles:

- Governance Staking
- cyGOV Yield Staking
- vlSDT Revenue Staking
- vlSDT Boost Staking
- Revenue Vault V7
- any additional deployed component whose ABI exposes a genuine
  deposit/stake-and-withdraw lifecycle

Each cycle uses one shared time advance:

1. Record starting timestamp, balances, shares, PPS where supported, and
   reward/accounting state.
2. Deposit or stake into every applicable contract.
3. Record post-deposit state.
4. Advance Anvil time by exactly 15 days and mine one block.
5. Record accrued rewards and PPS before harvesting.
6. Harvest or claim every available reward path.
7. Record harvested tokens, fees, PPS, and realized yield.
8. Withdraw or unstake all cycle positions.
9. Record returned principal, withdrawal fees, remaining shares/stake, claimed
   rewards, and net yield.

The opening cycle runs before the general ABI scenarios. Its resulting state is
the canonical baseline. Intermediate scenarios use snapshots so destructive
tests cannot corrupt that state. The closing cycle runs after all ABI scenarios
against the restored canonical state.

The JSON report will contain separate `openingCycle` and `closingCycle`
measurements per contract, including:

- deposited principal
- minted shares or stake
- PPS before deposit, before harvest, after harvest, and after withdrawal
- reward balances before and after
- accrued and claimed rewards
- harvest output
- withdrawal proceeds and fees
- principal delta
- net token-denominated yield
- elapsed time, blocks, and transaction gas

When a contract has no PPS concept, the field will be explicitly marked
`not-applicable`; staking yield will be reported from earned/claimed reward
deltas instead.

## Callable-Function Coverage

Each ABI signature receives one or more scenario records containing:

- contract key and deployed address
- canonical function signature
- caller role
- arguments in serialized form
- scenario category
- expected result
- actual result
- transaction hash and gas for writes
- return data for reads
- status

Valid terminal statuses are:

- `passed-success`
- `passed-expected-revert`
- `passed-deployment-configuration`
- `failed-unexpected-revert`
- `failed-unexpected-success`
- `failed-assertion`
- `blocked-precondition`

Any `failed-*`, `blocked-precondition`, or missing signature makes the overall
run fail. Expected-revert-only coverage is permitted only for functions whose
successful path is impossible or intentionally disabled in the deployed
design, and the report must state the reason.

## Error Reporting

Every call is wrapped by a common executor. On a revert it records:

- contract and exact signature
- scenario and expected outcome
- caller and arguments
- fork block, local block, and timestamp
- decoded Solidity custom error, revert string, or panic code
- raw revert data
- transaction hash when one exists
- concise `debug_traceTransaction` failure location when available

Unexpected reverts do not stop report generation immediately. The harness
continues independent scenarios, writes the full error report, and exits
nonzero at the end.

## Verification

Before delivery:

1. Clean-compile all 71 active Solidity files.
2. Run unit tests for ABI inventory completeness, result classification, error
   decoding, snapshot restoration, and 15-day cycle accounting.
3. Run JavaScript and static checks.
4. Run the complete harness once on the supplied public RPC-backed Anvil fork.
5. Require 100% classification of the dynamically generated ABI inventory and
   zero failed or blocked records.
6. Confirm both 15-day cycles completed for every applicable staking/vault
   contract.
7. Confirm no RPC URL, private key, generated fork state, dependency directory,
   build artifact, or cache is included in the delivered source package.
